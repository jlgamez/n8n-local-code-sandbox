# respond.io Architect

Apply this skill when assessing, designing, improving, or creating respond.io workflows.

---

## Workflow file conventions

respond.io workflow files live under `respond/workflows/`:

```
respond/workflows/
  <workflow-name>/
    <WorkflowName>.json        # original / v1
    <WorkflowName>_v2.json     # after first review
```

**Versioning rule** — when reviewing or improving a workflow, never overwrite the original:
- `Workflow.json` → save as `Workflow_v2.json`
- `Workflow_v2.json` → save as `Workflow_v3.json`

## Platform constraints (hard limits — memorise these)

| Constraint | Value | Notes |
|---|---|---|
| Max steps per workflow | **100** | Counts every node including branch connectors and jump-to |
| Max workflows per workspace | 150 | Growth, Advanced, Enterprise plans |
| HTTP request timeout | **10 s** (hardcoded) | No way to extend; design around it with async patterns |
| HTTP max headers | 10 | |
| HTTP response variable mapping | up to 10 | Per step `responseMap` array |
| Incoming webhook variables | **10 max**, 30-char name limit, 500-char max value | |
| Branch: max conditions per connector | 10 | Per branchConnector |
| Branch: max connectors (including Else) | 10 | 9 named + 1 Else |
| Jump To: max jumps | 10 (hard), ≤3 (recommended) | Counter resets on workflow exit |
| Ask a Question: multiple choice options | 10 options, 20-char each | |
| Wait / total workflow lifetime | **7 days** | Workflow auto-terminates at 7-day mark regardless of Wait steps |
| Contact field cache | **3 minutes** | `$contact.*` values are stale after 3 min inside a long-running workflow |
| Max workflow import file size | 400 KB | |
| Blacklisted HTTP domain | `respond.io` | Cannot make HTTP requests to respond.io itself |
| OAuth 2.0 in HTTP | Not supported | Use static API keys / tokens only |
| Self-signed SSL certs | Not accepted | HTTP step only |

## Workflow JSON top-level schema

```json
{
  "id": 1782900000000001,
  "name": "Workflow display name",
  "description": "Import notes, architecture summary, post-import checklist",
  "status": "draft",
  "publishedBy": null,
  "publishedAt": null,
  "updatedAt": 1783000000000,
  "createdBy": 1055930,
  "createdAt": 1783000000000,
  "connectedToWorkflows": [],
  "settings": {
    "manualEjection": true,
    "exitCondition": {
      "outgoingMessage": false,
      "manualAssignment": false,
      "incomingMessage": false
    }
  },
  "workflow": [ /* steps array */ ]
}
```

### `settings.exitCondition` options

| Key | Effect when `true` |
|---|---|
| `outgoingMessage` | Any outgoing message by a human agent stops the workflow (not workflow's own `sendMessage`) |
| `incomingMessage` | Any incoming contact message stops the workflow (not answers to `askQuestion`) |
| `manualAssignment` | Manual inbox reassignment stops the workflow (not API/workflow assignments) |

## Step JSON schema

Every step has this envelope:

```json
{
  "id": "hex6" | 1,
  "parentId": "hex6" | -1 | null,
  "type": "stepType",
  "name": "Display name",
  "data": { /* step-specific */ }
}
```

- The **trigger** step always has `"id": 1` (number) and `"parentId": -1` (or `null` for `incomingWebhook`)
- All other step IDs are 6-char lowercase hex strings (e.g. `"a3f09c"`)
- `parentId` always references the step whose output feeds into this step
- Branch connectors and ask-question connectors are separate steps with their own IDs

## Step types reference

### trigger
```json
{
  "type": "trigger",
  "data": {
    "type": "contactTagUpdated",
    "tag": 12345678,
    "oncePerContact": false,
    "conditions": [],
    "action": "tagAdded"
  }
}
```

**Trigger type values:**

| `data.type` | Notes |
|---|---|
| `contactTagUpdated` | `action`: `"tagAdded"` \| `"tagRemoved"` |
| `incomingWebhook` | Advanced plan+. URL auto-generated on import. Max 10 variables. Contact identifier via JSON path. |
| `manualTrigger` | No standalone use — only callable via `triggerWorkflow` step |
| `conversationOpened` | |
| `conversationClosed` | |
| `contactFieldUpdated` | |
| `shortcut` | Manual trigger from Inbox composer |
| `lifecycleUpdated` | |
| `callEnded` | |

**Incoming webhook trigger schema:**
```json
{
  "type": "incomingWebhook",
  "url": "https://app.respond.io/webhook/...",
  "contactIdentifier": {
    "path": "$.contact_id",
    "field": "id"
  },
  "variables": [
    { "variable": "callback_status", "path": "$.status" },
    { "variable": "slot_1_date",     "path": "$.slot_1_date" }
  ]
}
```
> ⚠️ The webhook URL is **generated by respond.io on import** — the placeholder URL in the file is replaced automatically. After import, copy the real URL into your n8n/external service config.
> ⚠️ The `variables` mapping may need to be re-configured in the UI after import — the JSON import schema is not fully stable for this field.

### sendMessage
```json
{
  "type": "sendMessage",
  "data": {
    "channelId": null,
    "connectors": [],
    "payload": [
      { "message": { "type": "text", "text": "Your message here" } }
    ]
  }
}
```
`channelId: null` = use the contact's last interacted channel.

---

### askQuestion
```json
{
  "type": "askQuestion",
  "data": {
    "connectors": ["successStepId", "failureStepId"],
    "question": {
      "type": "text",
      "options": [],
      "text": "Question text with {{$contact.firstname}}"
    },
    "timeout": { "value": 7, "unit": "days" },
    "saveResponse": {
      "tag": false,
      "field": "contact_field_name",
      "variable": null
    }
  }
}
```

For **multiple choice**: `"type": "multiple"`, `"options": ["1", "2", "3"]` (max 10 options, 20 chars each).

The `connectors` array references two `askQuestionConnector` child step IDs: `[successId, failureId]`.

```json
{ "type": "askQuestionConnector", "data": { "connectorType": "success" } }
{ "type": "askQuestionConnector", "data": { "connectorType": "failure" } }
```

**Failure branch triggers:** invalid format, wrong channel, timeout, API/network errors.

---

### branch + branchConnector
```json
{
  "type": "branch",
  "data": {
    "connectors": ["connId1", "connId2", "elseId"]
  }
}
```

Each `branchConnector` is a separate step parented to the `branch`:
```json
{
  "type": "branchConnector",
  "name": "Spanish",
  "data": {
    "conditions": {
      "$and": [
        {
          "category": "contactField",
          "field": "user_language",
          "operator": "isEqualTo",
          "value": "es"
        }
      ]
    }
  }
}
```

**Else connector** (always last, `conditions: null`):
```json
{ "type": "branchConnector", "name": "Else", "data": { "conditions": null } }
```

**Condition `category` values:** `contactField`, `variable`, `contactTags`, `assigneeStatus`, `lastInteractedChannel`, `lastIncomingMessage`, `lastOutgoingMessage`, `lastOutgoingMessageSource`, `timeSinceLastIncomingMessage`, `timeSinceLastOutgoingMessage`

**Operators:** `isEqualTo`, `isNotEqualTo`, `greaterThan`, `lessThan`, `between`, `exists`, `doesNotExist`, `contains`, `doesNotContain`, `hasNoneOf`, `hasAllOf`, `hasAnyOf`, `after`, `before`

Logic within a connector: `$and` or `$or`. Max 10 conditions per connector. Max 9 named connectors + 1 Else.

---

### jumpTo
```json
{
  "type": "jumpTo",
  "data": {
    "stepId": "targetStepId",
    "maxJumps": 1
  }
}
```
`maxJumps`: 1–10. Recommended ≤3. When the limit is hit, the contact skips the jump and proceeds to the step after `jumpTo`. Counter resets on workflow exit.

**Pattern:** Multiple language branches all `jumpTo` the same convergence step to avoid duplicating logic downstream.

---

### wait
```json
{
  "type": "wait",
  "data": {
    "unit": "seconds",
    "value": 3
  }
}
```
Units: `seconds`, `minutes`, `hours`, `days`. Max per step: 7 days. Total workflow lifetime: 7 days.

> ⚠️ No "wait until specific time" support — only relative durations.

---

### httpRequest
```json
{
  "type": "httpRequest",
  "data": {
    "method": "post",
    "url": "https://example.com/webhook",
    "contentTypeHeader": "application/json",
    "headers": [
      { "key": "Authorization", "value": "Bearer TOKEN" }
    ],
    "body": "{\n  \"contact_id\": \"{{$contact.id}}\"\n}",
    "responseMap": [
      { "variable": "result_status", "path": "$.status" }
    ],
    "saveResponse": {
      "variable": "http_status_code"
    }
  }
}
```

- `responseMap`: maps JSON-path fields from response body to workflow variables (max ~10)
- `saveResponse.variable`: captures the HTTP status code (e.g. `200`, `500`)
- Timeout: **hardcoded 10 seconds** — no override
- On failure: contact skips the step and continues; variables become `null`/`undefined`
- Cannot use respond.io's own domain as URL

### updateContactField
```json
{
  "type": "updateContactField",
  "data": {
    "contactField": "field_name",
    "contactFieldValue": "literal or {{$contact.other_field}} or {{$workflow.var}}"
  }
}
```
Interpolation syntax: `{{$contact.fieldname}}` and `{{$workflow.varname}}`.

### updateContactTag
```json
{
  "type": "updateContactTag",
  "data": {
    "action": "addTag",
    "value": [12345678]
  }
}
```
`action`: `"addTag"` | `"removeTag"`. `value`: array of tag IDs (integers).

### assignTo + assignToConnector
```json
{
  "type": "assignTo",
  "data": {
    "assignTo": "specificUser",
    "userId": 1055930,
    "teamId": null,
    "assignmentLogic": "RoundRobin",
    "connectors": ["successConnectorId"],
    "timeout": { "value": 7, "unit": "days" },
    "onlyOnlineUsers": false,
    "onlyUsersContactsLess": null
  }
}
```

`assignTo` values: `"specificUser"`, `"team"`, `"workspace"`, `"unassign"`
`assignmentLogic`: `"RoundRobin"` | `"LoadBased"` | `null` (for specificUser)

```json
{ "type": "assignToConnector", "data": { "connectorType": "success" } }
```

### triggerWorkflow
```json
{
  "type": "triggerWorkflow",
  "data": {
    "workflowId": 1782645075067929,
    "stepId": null
  }
}
```
`stepId: null` = start from the beginning of the target workflow. Can specify a step ID to jump to a mid-point.

> ⚠️ When two `triggerWorkflow` steps are placed consecutively they run **concurrently** — not sequentially. If sequential execution matters, add a `wait` step in between.
> ⚠️ Loop prevention: ensure triggered workflows don't circle back to trigger the origin workflow. The platform detects cycles at publish time.

## Variable system

### Syntax
| Scope | In step `data` strings | In branch conditions |
|---|---|---|
| Contact fields | `{{$contact.fieldname}}` | `category: "contactField", field: "fieldname"` |
| Workflow variables | `{{$workflow.varname}}` | `category: "variable", field: "varname"` |

### Workflow variables vs contact fields

| | Workflow variables | Contact fields |
|---|---|---|
| Declared by | HTTP `responseMap`, webhook `variables`, shortcut form, `saveResponse` in askQuestion/assignTo | Pre-existing custom fields in the workspace |
| Scope | Per workflow execution — cleared when workflow ends | Persistent on the contact record |
| Survive workflow end | No | Yes |
| Usable across workflows | No — pass via contact fields | Yes |

### Contact field caching
`$contact.*` values are **cached for 3 minutes** from when the workflow is triggered. If a long Wait step elapses, the cached values may be stale. Use `updateContactField` to write state, then read it back within the same workflow — but be aware the cache may not reflect changes made by concurrent workflows.

### Cross-workflow data passing pattern
Workflow variables cannot be passed between workflows directly. To hand off data:
1. In Workflow A: `updateContactField` to persist values you need downstream
2. In Workflow B: Read them via `$contact.fieldname`

## Architecture patterns

### 1. Async fire-and-forget + callback (the core async pattern)

Use when an external call (n8n, API) takes > 10 seconds.

**Workflow A — Dispatch:**
1. Send filler message ("checking availability…")
2. Set status flag: `updateContactField n8n_execution_status = "pending"`
3. `httpRequest` to external service (fire-and-forget — it will call back)
4. `wait` (2–3 min, tuned to expected processing time)
5. `branch`: is status still `"pending"`?
   - YES (timeout): set status to `"failed_timeout"`, `triggerWorkflow` to error handler
   - Else: silent exit (callback already handled it)

**Workflow B — Callback (incomingWebhook trigger):**
1. Idempotency guard `branch`: is status still `"pending"`?
   - Else: exit (A already timed out and handled it)
2. `branch` on callback payload status (`error`/`success`/Else→error)
3. On success: process result, proceed to user interaction
4. On error: set status to `"failed_error"`, `triggerWorkflow` to error handler

**Why the idempotency guard:** A's timeout branch and B's callback can arrive at almost the same time. Checking `n8n_execution_status == "pending"` at the top of B prevents double-processing.

**Why the "Block AI" assignTo before the HTTP call:** Assigning to a specific user (e.g. an AI Agent user) before the HTTP request prevents the contact from being grabbed by another workflow or agent during the wait window.

### 2. Receiver + Presenter split (step-count management)

When a single callback workflow would exceed 100 steps (because it handles both receiving data and presenting per-language messages), split it:

- **B-1 Receiver**: Handles the webhook, idempotency guard, error/no-slots paths, persists slot data to contact fields via `updateContactField`, then `triggerWorkflow` → B-2
- **B-2 Presenter**: Reads slot data from `$contact.*` fields, presents options to user, handles user pick

This is necessary when language-branch × slot-option combinations push the step count past 100.

### 3. Language branching with jumpTo fan-in

Pattern for multi-language messages without duplicating downstream logic:

```
branch (language)
├── es → sendMessage ES → jumpTo [common step]
├── en → sendMessage EN → jumpTo [common step]
├── ru → sendMessage RU → jumpTo [common step]
├── ca → sendMessage CA → jumpTo [common step]
└── Else → sendMessage default → (first step in chain, others jump here)
```

The Else branch's child step IS the common step that all `jumpTo` steps target. This avoids duplicating the continuation logic N times.

### 4. Security wait before sensitive reads

Add a 2–3 second `wait` step before reading contact fields that were just written by a concurrent or just-completed workflow. This guards against race conditions in the contact field cache.

```
[askQuestion] → [wait 2s] → [branch on answer]
```

### 5. Error escalation pattern

Standardise error paths:
1. `updateContactField failure_source_workflow = "workflow name"`
2. `updateContactField n8n_execution_status = "failed_error"` (or `"failed_timeout"`)
3. `triggerWorkflow` → common "derive to human" workflow

This lets the error handler workflow know where the failure originated.

### 6. Tag-based workflow chaining (re-trigger pattern)

To re-run Workflow A from within Workflow B (e.g. after a no-slots retry):
1. Workflow A is triggered by a tag
2. Workflow B removes the tag if present, then re-adds it
3. The `contactTagUpdated` trigger on Workflow A fires again

Always add a short `wait` (≥3 s) before re-adding the tag to avoid the trigger being swallowed.

## Reviewing a workflow

When asked to review or improve an existing respond.io workflow:

1. **Count steps** — flag if approaching or exceeding 100. Suggest splitting into sub-workflows via `triggerWorkflow` + `manualTrigger`.
2. **Check HTTP steps** — confirm that any calls expected to take > 10 seconds use the async pattern instead of a synchronous `httpRequest`.
3. **Check idempotency** — callback workflows triggered by external webhooks should guard against double-execution.
4. **Check error paths** — every `httpRequest`, `askQuestion`, and `assignTo` should have a handled failure path (not just silent skip).
5. **Check variable scope** — are cross-workflow data needs met via contact fields? Workflow variables don't survive workflow exit.
6. **Check step count budget** — each language × option combination multiplies steps. 4 languages × 3 options = 12 `askQuestion` steps alone; plan around the 100-step limit.
7. **Check loop risk** — workflows that `triggerWorkflow` each other must not cycle. Verify idempotency guards and status flags prevent re-entry.
8. **Check tag cleanup** — if a tag is used to trigger a workflow, the first step should remove that tag to prevent re-triggering if the tag is re-applied later in the same run.

## Creating a new workflow

1. Start the `workflow` array with the trigger step (`"id": 1`, `"parentId": -1`).
2. Generate unique 6-char hex IDs for all other steps.
3. Build the parentId chain: each step's `parentId` is the step that flows into it.
4. Branch: `branch` lists connector IDs in `data.connectors`; each `branchConnector` step has the `branch` as its `parentId`.
5. Always include an Else `branchConnector` (`conditions: null`).
6. Keep `status: "draft"` — never set `"published"` in the JSON file; publish via the UI.
7. Put import instructions in `description`: which IDs to update (tag IDs, user IDs, workflow IDs), and what to re-configure post-import (webhook URL, variable mapping).
8. Use placeholder IDs (`99999999` for tags, `1055930` for users) and document them in `description`.

## Gotchas

- **`triggerWorkflow` is fire-and-forget**: it does not pause the current workflow. If you need sequential execution, add a `wait` or use a contact field as a semaphore.
- **Consecutive `triggerWorkflow` steps run concurrently**, not in order.
- **Importing contacts with tags doesn't fire `contactTagUpdated`** — the trigger only fires on real-time tag additions.
- **`incomingWebhook` URL is regenerated on import** — any external service must be updated with the new URL after import.
- **Media content is not accessible** — `$contact.last_incoming_message` returns file *type* only (image/video/audio), not the URL.
- **`$contact.*` is cached for 3 min** — in workflows with long waits, field values may be stale. Use contact fields for inter-workflow state, but add security waits for reads after writes.
- **Step count includes connectors** — every `branchConnector`, `askQuestionConnector`, and `assignToConnector` counts toward the 100-step limit.
- **`manualTrigger` workflows can only be started by `triggerWorkflow`** — they have no autonomous trigger.
- **Workflow stops when it reaches 7 days** — total elapsed time, not just explicit Wait steps. An `askQuestion` with a 7-day timeout + previous waits may auto-terminate.
- **Testing not available** for Custom Channel and WeChat.
- **The `respond.io` domain is blacklisted** in HTTP Request URLs — you cannot make self-calls.
